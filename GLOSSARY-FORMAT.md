# GLOSSARY.md Format

`GLOSSARY.md` is the canonical language for this course. All lessons, exercises, and learning records should adhere to its terminology. Building it is itself part of learning: compressing a concept into a tight definition is evidence the learner understands it.

## Structure

```md
# {Topic} Glossary

{One or two sentence description of the topic this glossary covers.}

## Terms

**Term**:
Tight, one-or-two-sentence definition of what the term IS, not what it does or how to do it.
_Avoid_: alternate phrasings this workspace has deliberately standardized away from

**Another term**:
Definition, ideally using other glossary terms where that makes it clearer.
_Avoid_: looser synonyms in casual use elsewhere
```

## Rules

- **Add a term only when the learner understands it.** The glossary is a record of compressed knowledge, not a dictionary they read to learn from. Wait until they can use it correctly, not merely after they've been introduced to it — see the Feynman Check in `SKILL.md`.
- **Be opinionated.** When several words exist for the same concept, pick the best one and list the rest as aliases to avoid. This is how language compresses.
- **Keep definitions tight.** One or two sentences. Define what the term IS.
- **Use the glossary's own terms inside later definitions.** This is what makes complex terms easier to grasp once the vocabulary is established.
- **Group under subheadings** when natural clusters emerge. A flat list is fine when terms cohere.
- **Flag ambiguities explicitly.** If a term is used loosely in the wider field, note this workspace's resolution.
- **Revise as understanding deepens.** A definition written early may be wrong later. Update in place; don't leave stale entries.
